# MCHOSE V9 Turbo+ 灯控协议

测试设备：**迈从 V9 Turbo+**（USB 有线/2.4G 耳机）。
灯控走 `0x3837:0x6008`（WCH 主控），**不是** `0x600A`（C-Media 7.1 声卡）。

## 1. HID 接口

| 项 | 值 |
|---|---|
| VID:PID | `0x3837:0x6008` |
| product | `V9 Turbo`（mfr `wch.cn`） |
| usage_page | `0xFF00`（该设备只有这一个 HID 集合） |
| 输入/输出报告长度 | 65 字节（HidP_GetCaps 实测） |
| report id | **0**（线上第 1 字节 `0xAA` 是报文内容，不是 report id） |

## 2. 报文（64 字节数据 + 1 字节 report id 0）

```
偏移  值
[0]   0xAA            magic / 报文头
[1]   0x27            设色命令（0x07 = 状态查询）
[5]   0x0A
[6]   0x01
[7]   mode            0 常亮 / 1 呼吸 / 2 繁星 / 3 循环 / 4 随波
[8]   0x05
[9]   direction       方向（随波模式用）
[10]  brightness      0..3（官方取 3）
[11]  0x00
[12..14] R G B
[15..63] 0
```

## 3. 写入方式的坑（最重要）

| 方式 | 结果 |
|---|---|
| `HidD_SetOutputReport(handle, buf, 65)`，buf = `[0x00] + 64 字节` | 返回 TRUE、收到 ACK，**颜色不变** |
| `WriteFile(handle, buf, 65)`，同上 | **生效** |
| `WriteFile(handle, 64)` / 63 字节 | 不生效 |
| `HidD_SetOutputReport(..., 64)` | 不生效 |

结论：**Windows 上必须走中断 OUT 端点（WriteFile），且缓冲是 65 字节（首字节 0 为 report id）。**

复现：`tools/headset_test.exe`，它会依次用四种方式写不同颜色，并用 `0x07` 读回 RGB 对照。

## 4. 读写同句柄 + 排空 ACK

设备每收到一条输出报告都会在输入端点回一个包。如果使用**两个句柄**（一个写、另一个读），
ACK 会积压在被写句柄的队列里，没人排空；队列满后固件**静默停止接受新帧**，而 API 仍返回成功。

误导性症状：

- 单次写、间隔 2.5 s → 有效；
- 连续写、间隔 0.4 s → 完全不动。

正确做法：**同一个句柄读写**，每次写完用非阻塞/短超时读把 ACK 排空（后台线程持续排空也可以）。

## 5. 0x07 状态查询（客观验证）

发送 `0x07`（同样用 WriteFile 65 字节），设备回包：

```
00 AA 07 02 00 00 1E 01 00 06 00 03 00 <R> <G> <B> ... 56 39 20 54 75 72 62 6F ("V9 Turbo") ...
```

- RGB 在 **offset 13..15**；
- `0x07` 命令本身也建议用 WriteFile 发；用 SetOutputReport 发时可能读不到回包。
- 写红 `(255,0,40)` → 读回 `255,0,40`；写蓝 `(0,40,255)` → 读回 `0,40,255`（实测）。

## 6. 节流与同步

- 耳机是固件渲染单区设备：只能整机一个颜色 + 固件模式。
- 应用 30 fps 运行时，没必要每帧都写：约 **20 Hz** 更新即可（`MIN_INTERVAL ≈ 50 ms`），
  颜色没变时跳过写入，减少 USB 压力。
- 固件模式（呼吸/繁星/循环/随波）下设备自己动画，不能与另外两台逐帧同步；要同步请用常亮模式。

## 7. 逆向过程

1. HID 路线长期“命令正确但灯不变”，最后用 **USBPcap** 抓官方客户端流量确认报文。
2. 官方客户端走 libusb 直接发 63 字节短包；HID 类驱动表达不了这个长度，但改用 65 字节 WriteFile 后可用。
3. USBPcap 解析注意 **headerLen 是字段**（本机中断 27 / control 28），硬编码会吞掉 report id `0xAA`。
